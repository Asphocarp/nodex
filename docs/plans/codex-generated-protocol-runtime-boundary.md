# Make generated Codex protocol schemas the single wire-contract authority

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document must be maintained in accordance with `docs/PLANS.md`. A contributor should be able to resume the migration from this file alone, without relying on conversation history or external notes.

## Purpose / Big Picture

Nodex talks to `codex app-server` over newline-delimited JSON-RPC. The repository already commits TypeScript bindings generated by the installed `@openai/codex` package, but several runtime validators and local interfaces repeat the same protocol by hand. Those copies can silently fall behind when a new Codex version adds a notification, thread item, approval field, reasoning effort, service tier, or decision variant. The most serious current example is that the local file-change approval path accepts command-only network and execution-policy amendments.

After this migration, upgrading `@openai/codex` and running one generator command will refresh both TypeScript bindings and a small set of runtime JSON Schemas. Incoming app-server messages and thread items will be checked against those generated schemas before Nodex consumes them. Protocol method and parameter pairs will remain discriminated unions from the process boundary through main-process routing and renderer delivery, so TypeScript will reject a handler that combines one method with another method's payload. Nodex-specific view models, persistence adapters, and private app-server extensions will remain local, but their names and boundaries will make that ownership explicit.

The result is observable without a visual UI change. `pnpm run codex:schemas:generate` followed by `pnpm run codex:schemas:verify` must be stable; tests must accept representative current app-server messages and reject malformed or mismatched ones; TypeScript must reject command-only decisions on a file approval; and the repository-wide structural audit described below must find no remaining parallel definitions for generated protocol shapes.

## Surprises & Discoveries

- Observation: The Codex TypeScript generator does not emit the generic JSON-RPC envelope types, while the JSON Schema generator does emit `JSONRPCMessage`, `JSONRPCRequest`, `JSONRPCNotification`, `JSONRPCResponse`, `JSONRPCError`, and `RequestId`.
  Evidence: A temporary `generate-json-schema --experimental` run produced standalone definitions for all six names; the corresponding `generate-ts` output exposes `RequestId` but not a complete `JSONRPCMessage` union.

- Observation: Zod 4.4.3 can convert draft-07 JSON Schema, but its local-reference resolver cannot directly follow nested references such as `#/definitions/v2/ErrorNotification` in the complete Codex bundle.
  Evidence: Direct conversion failed with `Reference not found: #/definitions/v2/ErrorNotification`. A prototype that copied the transitive reference closure into one flat `definitions` object and rewrote each JSON Pointer succeeded.

- Observation: A small generated artifact set is sufficient. Committing every JSON Schema file would add roughly four megabytes and hundreds of files, while the self-contained roots needed by Nodex are roughly one hundred and sixty kilobytes in total.
  Evidence: The temporary CLI output contained 337 files. Extracted `ThreadItem`, `ServerNotification`, `ServerRequest`, `ClientRequest`, and `JSONRPCMessage` roots compiled successfully and rejected an unknown union variant.

- Observation: The renderer-to-main owner request facade is not a raw Codex `ClientRequest` tunnel even though it uses Codex method names. Some params contain Nodex concepts such as a prompt string and `clientUserMessageId` that the main process later translates into one or more app-server requests.
  Evidence: `src/main/codex/codex-service.ts` reads custom params for owner `turn/start`, `thread/fork`, and related operations before constructing actual app-server requests. Therefore this facade needs a local typed action union, not a false alias to generated `ClientRequest`.

- Observation: The local `CodexApprovalDecision` union equals the broader command-execution decision and is reused for file changes.
  Evidence: Generated `FileChangeApprovalDecision` excludes `acceptWithNetworkPolicyAmendment` and `acceptWithExecpolicyAmendment`, but current shared and IPC types allow both values whenever the separate `kind` field says `file`.

- Observation: Native-module validation alternates between Node ABI 137 and Electron ABI 143; the repository main suite must use an Electron-targeted rebuild after any plain Node rebuild of `better-sqlite3`.
  Evidence: A plain `pnpm rebuild better-sqlite3` made Node-side checks load but caused Electron to reject ABI 137. Running the installed `@electron/rebuild` CLI against Electron 40.10.4 restored ABI 143, after which all 385 focused `codex-service` tests passed.

- Observation: The duplicate audit found more than the originally visible type aliases. Renderer owner ingress manually revalidated nearly every generated notification payload, transcript normalization repeated Guardian and collaboration-agent enums/state, project-session persistence used unconstrained status strings, and IPC/UI helper types repeated collaboration-mode and thread-status unions.
  Evidence: The migration removed the owner payload parsers, replaced Guardian/collaboration/status/goal validators with generated runtime roots, derived project-session and IPC fields from generated aliases, and made the structural searches for the removed parsers, synthetic methods, and literal protocol unions empty except for explicitly transformed app-domain/view-model types.

- Observation: The upstream TypeScript and JSON Schema generators differ on requiredness for several defaultable or nullable `ThreadItem` fields. For example, generated TypeScript requires `userMessage.clientId`, while the generated JSON Schema permits it to be omitted; the same pattern appears for nullable agent-message metadata and defaulted command/MCP fields.
  Evidence: A TypeScript-AST-to-JSON-Schema comparison covered all inline `ThreadItem` variants and found seven variants with TypeScript-only required keys. Full tests initially failed because old assertions treated omitted `clientId`, `phase`, or `appContext` as malformed even though the current generated runtime schema accepts them.

## Decision Log

- Decision: Generate runtime JSON Schemas from the installed Codex CLI instead of maintaining Zod enumerations by hand.
  Rationale: The CLI output and TypeScript bindings then describe the same installed app-server version. Zod remains the runtime validation library already used by the repository; no additional production dependency is required.
  Date/Author: 2026-07-15 / Codex

- Decision: Commit only deterministic, self-contained schema roots that Nodex actually imports, not the CLI's complete JSON Schema directory.
  Rationale: Runtime consumers need a handful of roots. Flattening each root's transitive local-reference closure keeps imports independent, makes renderer bundles pay only for schemas they use, and avoids committing hundreds of irrelevant files.
  Date/Author: 2026-07-15 / Codex

- Decision: Run both official generators in temporary directories and replace committed outputs only after every command and extraction step succeeds.
  Rationale: The existing generator deletes committed output before invoking the CLI. Transactional replacement makes a failed upgrade retryable and prevents a half-generated protocol package.
  Date/Author: 2026-07-15 / Codex

- Decision: Treat generated unions as closed at live runtime boundaries and treat private or synthetic Nodex messages as separate explicit unions.
  Rationale: Casting an unknown method to `ServerNotification` defeats runtime validation. Nodex-private option-picker, setup-picker, inbox, and synthetic terminal events are legitimate extensions, but they must have their own schema and type rather than weakening the generated union.
  Date/Author: 2026-07-15 / Codex

- Decision: Preserve `method` and `params` in the same discriminated object throughout routing and buffering.
  Rationale: Passing them as separate arguments turns correlated generated payloads into `string` and `unknown`, forcing unsafe reconstruction casts and allowing mismatched pairs. Whole-object routing lets an ordinary `switch` narrow the exact params type.
  Date/Author: 2026-07-15 / Codex

- Decision: Keep product projections and compatibility adapters local only when they transform the generated contract, and name the transformation explicitly.
  Rationale: `ThreadSummary`, account snapshots, canonical conversation state, and persisted historical payload adapters have Nodex semantics. Exact copies such as token usage, user-input options, collaboration mode, active flags, and approval decisions do not.
  Date/Author: 2026-07-15 / Codex

- Decision: Widen protocol-facing reasoning effort and service tier types to the generated string-based contract, with renderer label fallbacks for values unknown to the current UI build.
  Rationale: The app server reports model-supported values dynamically. A hard-coded local enum causes a successful Codex upgrade to drop new supported values before the UI can display them.
  Date/Author: 2026-07-15 / Codex

- Decision: Do not retain permissive live-notification adapters for snake_case fields, missing `turnId`, partial `Turn`, or synthetic `turn/interrupted` / `turn/failed` methods.
  Rationale: The generated JSON-RPC boundary already rejects those values, and keeping a second permissive protocol in renderer/main tests hides schema drift. Persistence migrations and Nodex synthetic state remain separate, explicitly named adapters.
  Date/Author: 2026-07-15 / Codex

- Decision: Follow the generated JSON Schema's `required` lists at runtime instead of adding a handwritten strictness overlay to imitate generated TypeScript requiredness.
  Rationale: The runtime artifact describes what the serde-backed wire can omit and is refreshed automatically with the pinned CLI. Requiring nullable/defaulted keys locally would recreate the parallel schema this migration removes; tests now use fields that the generated artifact itself marks required when proving fail-closed behavior.
  Date/Author: 2026-07-15 / Codex

## Outcomes & Retrospective

The migration now has one generated wire-contract authority. The pinned CLI transactionally produces TypeScript plus 20 self-contained runtime-schema roots; live JSON-RPC, notifications, requests, thread items, approval decisions, thread status/goal/token usage, Guardian review, and collaboration-agent state validate from those artifacts. Complete notification objects retain their discriminants through resume buffers, main routing, owner IPC, MCP fallback, renderer queues, and reducers. The renderer-to-main owner facade is a separate local discriminated orchestration union whose true pass-through params reuse generated types.

The repository-wide audit removed exact aliases and less obvious runtime duplication: permissive owner payload parsers, handwritten Guardian/collaboration enums and state, project-session status strings, IPC collaboration-mode literals, thread-section/command-palette status strings, and obsolete missing-field tests. Remaining local Codex-prefixed interfaces are intentional projections, persistence records, request cards, or orchestration inputs that add, rename, omit, or derive fields; they are not accepted as raw app-server envelopes.

The final tree passes schema verification, strict type checking, lint, all 5,221 tests, and the production build. No `CHANGELOG.md` entry was added because the migration changes an internal protocol boundary and upgrade workflow without adding a user-visible feature. Future Codex upgrades now have one deterministic regenerate/verify path, and new protocol variants remain correlated through routing instead of degrading into `string` plus `unknown`.

## Context and Orientation

Nodex is an Electron application. The Electron main process owns a long-lived `codex app-server` subprocess and reads one JSON value per stdout line. The renderer never talks to the subprocess directly; it uses IPC and main-process facades. “Protocol” in this plan means the public JSON request, response, and notification shapes spoken by that subprocess. A “discriminated union” means a TypeScript union whose `method` or `type` field selects the exact shape of the remaining fields.

`package.json` pins `@openai/codex` and exposes `codex:schemas:generate` and `codex:schemas:verify`. `scripts/codex-schemas.ts` locates the package's CLI and invokes `app-server generate-ts --experimental`. The committed TypeScript output lives in `packages/codex-app-server-protocol/src`, with `packages/codex-app-server-protocol/src/v2` serving as the source of truth for request, response, notification, thread, turn, and approval types. `packages/codex-app-server-protocol/package.json` exposes those bindings to the rest of the workspace.

The Codex CLI can also generate draft-07 JSON Schemas. Its complete output contains a large aggregate schema and many standalone schemas. References inside aggregate roots can point into nested paths such as `#/definitions/v2/...`. The runtime artifact extractor must resolve JSON Pointer escape rules (`~1` means `/` and `~0` means `~`), discover every transitive local `$ref`, copy each referenced definition under a deterministic flat name, and rewrite `$ref` values to that flat name. Definitions and object keys must be serialized in a stable order so verification is byte-for-byte repeatable.

`src/main/codex/codex-app-server-client.ts` owns the subprocess transport. It currently parses JSON into local JSON-RPC interfaces, recognizes notifications by the presence of `method`, then casts them to generated `ServerNotification`. It also accepts generated `ServerRequest` values and three intentional private request families: inbox item creation, an option picker, and a setup-context picker. This file is the first trust boundary and must validate the complete envelope before emitting typed events.

`src/shared/codex-protocol-thread-item.ts` is a second trust boundary used when thread-item values cross storage or IPC. It currently contains a large handwritten validator for every known `ThreadItem` variant. Replace its implementation with a compiled generated `ThreadItem` runtime schema while preserving its small public parse/guard API so callers stay simple.

`src/shared/schemas/codex.ts` contains Zod schemas used for stored collaboration modes, active flags, reasoning effort, and token usage. Some are exact protocol copies; some accept old snake_case persisted data. Live protocol validation and persistence compatibility are different responsibilities. Generated current schemas belong in the live boundary. If existing databases need old spellings, retain a narrowly named persistence adapter beside the store that reads them, then convert to the generated current shape.

`src/shared/types.ts` is the application-wide type hub. It currently declares exact copies or narrower shadows of generated types, including collaboration mode kinds, turn status, token usage, patch kinds, approval decisions, user-input options, service tiers, and reasoning effort. Exact copies must become imports, re-exports, indexed-access aliases, or generated `Pick` projections. A local shape may remain only if it is a genuine view model or domain transformation and its name and comment state that fact.

`src/main/codex/codex-service.ts` routes validated notifications into canonical conversation state, lifecycle state, persistence, renderer forwarding, and owner resume buffers. It currently accepts `method: string` and `params: unknown`, then repeatedly casts reconstructed objects back to `ServerNotification`. Buffers also split method and params. Change those seams to carry one full notification object. Helper handlers should accept an `Extract<ServerNotification, { method: ... }>` when they only support selected methods. Unknown live protocol messages must not enter canonical reducers as if they were valid generated messages.

`src/shared/codex-thread-owner-notifications.ts`, `src/main/ipc/codex-ipc.ts`, `src/preload/index.ts`, `src/renderer/lib/app-server-message-bus.ts`, and `src/renderer/stores/local-conversation-store.ts` form the main-to-renderer owner notification path. The owner allowlist is intentional because not every app-server notification needs renderer delivery, but its union must be derived with `Extract` from `ServerNotification` and combined with explicitly declared Nodex synthetic notifications. IPC host messages should contain that whole union object rather than unrelated `method` and `params` fields.

The reverse renderer-to-main owner action path begins in `src/renderer/lib/renderer-owner-app-server-request-client.ts`, crosses shared IPC types, and reaches the owner request handler in `src/main/codex/codex-service.ts`. Its current envelope is `{ method, params: unknown }`. Define a local discriminated `CodexThreadOwnerActionRequest` union with exact params for every operation. Where an operation is a direct Codex request, derive params from `Extract<ClientRequest, { method: ... }>`; where it is orchestration, name and type the Nodex input explicitly. Provide a conditional result mapping so the renderer client cannot ask for an arbitrary result type.

Approvals cross the same layers. Generated command approvals accept `CommandExecutionApprovalDecision`; generated file approvals accept the narrower `FileChangeApprovalDecision`. Replace the separate `kind` and broad `decision` arguments with a single union such as `{ kind: "command"; decision: CommandExecutionApprovalDecision } | { kind: "file"; decision: FileChangeApprovalDecision }`. Keep request id and conversation id outside or alongside this union, but never separate the discriminator from the decision it constrains.

## Validation and Acceptance

Schema generation is accepted when a clean checkout can run `pnpm run codex:schemas:generate` twice, see no second-run diff, and then pass `pnpm run codex:schemas:verify`. Changing the pinned `@openai/codex` version in a future branch and regenerating must update both TypeScript files and only the runtime roots whose reachable Codex definitions changed.

The transport boundary is accepted when a valid current notification such as `turn/plan/updated` reaches a typed listener, a valid current approval request reaches its handler with all required fields, and a method paired with invalid params produces the client's malformed-message path without reaching service reducers. A success response and an error response must both settle the matching pending request; an envelope with neither or both result and error must be rejected.

Thread-item validation is accepted when representative variants from the generated union parse, a nested field with the wrong type fails, and a value with an unknown `type` fails. The test should derive fixtures or compile-time coverage from the generated union where practical so adding a new generated variant produces an actionable test or exhaustive-switch failure instead of silent default rejection.

Approval handling is accepted when command approvals can send every generated command decision, file approvals can send every generated file decision, and a file approval carrying a network-policy or execution-policy amendment is rejected before the app-server response is written. The shared API must make the invalid combination impossible in normal typed code.

Notification routing is accepted when the same discriminated object is carried through initial parsing, buffering during owner resume, main routing, IPC host messages, renderer bus delivery, and canonical reducer entry. There must be no cast that reconstructs a generated notification from a free `string` and `unknown`. An owner-notification allowlist may remain, but its listed methods must be statically checked against `ServerNotification["method"]` and its params must be derived by `Extract`.

The type-duplication audit is accepted when exact local aliases point to generated types, protocol-facing dynamic strings are no longer filtered by stale literal enums, and each remaining near-protocol local interface has a documented transformation purpose. Product view models such as thread summaries and account snapshots may remain because they intentionally select, rename, aggregate, or add fields.

The entire migration is accepted only when `pnpm run codex:schemas:verify`, `pnpm run typecheck`, `pnpm run lint`, `pnpm test`, and `pnpm run build` all pass on the final tree and the plan is updated with their actual outcomes.

## Idempotence and Recovery

Schema generation must be safe to repeat. It should write official CLI output and extracted roots under temporary directories, validate that all required roots exist and compile structurally, then replace committed output directories. If the CLI fails, the installed package is missing, or extraction encounters an unresolved or non-local reference, exit nonzero and leave committed files untouched. Always remove temporary directories in `finally` blocks.

Verification must never modify committed output. It should generate into a temporary directory, compare normalized relative paths and bytes, print actionable missing, extra, or changed paths, and clean up. A developer recovers from a version mismatch by running `pnpm install` followed by `pnpm run codex:schemas:generate` and reviewing the generated diff.

Runtime schema compilation is deterministic and happens once per module load. If Zod cannot compile a committed generated artifact, fail loudly during development or process startup rather than falling back to a permissive cast. Do not catch validation errors and silently reinterpret invalid generated messages as valid private messages; only explicitly recognized private methods may take that branch.

The code migration should proceed additively: introduce generated validators and typed unions, migrate call sites, then delete handwritten definitions. If a checkpoint fails, fix forward from the last passing commit. Do not use destructive Git reset or overwrite unrelated work. The repository has no production user data, so no database migration compatibility layer is required beyond reading formats the current repository deliberately persists and tests.

## Interfaces and Dependencies

Continue using `@openai/codex` as the sole upstream protocol source and `zod` 4.4.3 as the existing runtime validator. Do not add Ajv or another JSON Schema runtime unless Zod proves unable to compile a required extracted root and that failure is recorded in `Surprises & Discoveries` with a reproducible test.

`scripts/codex-schemas.ts` must expose its current command-line contract:

    pnpm run codex:schemas:generate
    pnpm run codex:schemas:verify

Internally, give extraction helpers pure inputs and outputs so they can be unit tested. A suitable conceptual interface is:

    extractSchemaRoot(bundle: JsonSchemaObject, rootName: string): JsonSchemaObject

The returned object must contain the selected root schema, a draft declaration compatible with the source, and a flat deterministic `definitions` closure with rewritten local references. The implementation may use more precise internal types, but must reject unresolved refs and duplicate flat names.

Add a generated-schema adapter with a narrow conceptual interface:

    createGeneratedSchema<T>(artifact: unknown): z.ZodType<T>

The helper must call `z.fromJSONSchema` using draft-07 behavior and keep the unsafe generic assertion contained in this one reviewed seam. Callers import an individual JSON artifact and export a named typed schema. Do not place every artifact in one eagerly imported index module.

The app-server client must emit complete generated values:

    onNotification(listener: (notification: ServerNotification) => void): () => void
    setServerRequestHandler(handler: (request: CodexServerRequest) => Promise<unknown>): void

`CodexServerRequest` may remain `ServerRequest | CodexPrivateServerRequest`, where `CodexPrivateServerRequest` is a discriminated union of separately validated Nodex extensions. Generic JSON-RPC responses must be represented as a success-or-error union so `result` and `error` cannot both be optional.

The thread-item adapter must continue to offer a small typed API equivalent to:

    isCodexProtocolThreadItem(value: unknown): value is ThreadItem
    parseCodexProtocolThreadItem(value: unknown): ThreadItem | null

The implementation must delegate to the generated `ThreadItem` runtime schema and must not switch over a handwritten list of item types.

The owner notification contract must be a full object union. A suitable shape is:

    type CodexThreadOwnerProtocolNotification = Extract<
      ServerNotification,
      { method: CodexThreadOwnerProtocolNotificationMethod }
    >

    type CodexThreadOwnerNotification =
      | CodexThreadOwnerProtocolNotification
      | CodexSyntheticThreadOwnerNotification

IPC host messages and renderer bus events must contain `notification: CodexThreadOwnerNotification`, not independent `method` and `params` fields.

The approval response contract must correlate kind and decision:

    type CodexApprovalResponse =
      | { kind: "command"; decision: CommandExecutionApprovalDecision }
      | { kind: "file"; decision: FileChangeApprovalDecision }

All renderer, preload, IPC, and main APIs must accept this union intact. If a function also needs a request id and conversation id, place those beside `response: CodexApprovalResponse` or intersect them with each union member; do not widen the decision again.

The owner action facade must define `CodexThreadOwnerActionRequest` and a conditional result mapping. Its exact variants should follow the inventory found during implementation. Generated request params should be derived with `Extract<ClientRequest, { method: M }>["params"]` only when the facade operation is a true one-to-one pass-through; orchestration inputs must remain explicit Nodex domain types.
