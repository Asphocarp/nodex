# Workbench Shell

## Intent
The workbench shell presents each Project as a folder in the left sidebar. Expanded Projects show durable Project-owned Sessions. Each Window Session renders the active Session as a Thread page with its own right and bottom panel view, replacing the previous stage rail with a denser desktop shell. Core-backed Session and Thread data remains shared; panel and tab arrangement does not synchronize across windows.

Detailed Auto-review preset, config, and approval-lifecycle rules are specified in [Auto-review Behavior](./auto-review-behavior.md).

## Layout
- Left sidebar: projects render as expandable folders. Selecting a project expands it and switches the DB project context.
- Project children: each expanded project lists ordered sessions. New projects start with one ordinary pinned `Database View` session.
- Sidebar footer: a compact Settings button remains available without workspace switching controls.
- Active session header: uses the active thread title row as the session header, without a separate session title, project-name subtitle, or empty toolbar row above it in either regular or narrow layouts. The fixed global header owns the left chrome (`Sidebar`, `Back`, `Forward`, and collapsed-only `New chat`) plus the top-right `Toggle bottom panel` and `Toggle side panel` controls, ordered bottom first and side second. Those persistent titlebar controls stay above and clickable over regular and full-width right panels, including collapsed-sidebar/full-width-panel layouts. Right-panel tab creation and expand/restore actions belong to the right-panel tab header; the expand/restore button is in the tab header's after-list flow with a measured trailing spacer matching the fixed right header slot. Bottom-panel tab creation plus the plain `Close` X action belong to the bottom-panel tab header. There is no attach/detach thread toolbar button.
- Thread page: the main session viewport always hosts the session thread page. If no thread is attached, it shows the new-thread composer. If the right panel is collapsed, the global top-right side-panel toggle opens it.
- Pinned summary: attached-thread pages show a summary button at the right edge of the thread header, immediately before the right-panel boundary. While the right panel is collapsed, the button is labelled `Toggle pinned summary` and controls the 300px pinned summary panel, which renders below the thread header and never over the top toolbar buttons. Opening the regular right panel hides the pinned overlay, makes the global header slot reserve the right-panel width, and switches the thread-header button to a separate `Toggle summary` popover trigger; that popover dismisses on outside click and does not change the saved pinned-open preference.
- Right panel: the right panel renders Window Session-local ordered tabs and split groups. It can be collapsed, regular-width, or expanded to the full Session content area. Newly materialized chat Session views start with the right panel collapsed; a Project database-starter `Database View` Session materializes one local open full-width DB tab targeting the Project's current primary Database default View when that Window Session has no saved view. Hiding and showing the side panel preserves that Window Session's regular/full-width mode. When the sidebar is collapsed and the right panel is full-width, the tab header reserves the measured left titlebar rail before the tabs so `Show sidebar`, Back, Forward, and compact `New chat` never overlap right-panel tabs. The persisted layout shape supports split leaves; header start reservation applies only to the top-left group and trailing expand/restore controls apply only to the top-right group.
- Full-width attached root-thread right panels render the shared thread composer as a fixed floating bottom overlay for `review`, `browser`, `db_view`, and `page_stage` tabs. A body portal mirrors the full-width pane rect, follows zoom and `--app-shell-bottom-panel-height`, and scopes pointer input to the centered composer group. Normal floating surfaces preserve 118px pane scroll clearance. Browser instead owns its zero-reserve compact/reveal presentation, with a 384px idle/hover width, focus expansion, and explicit hide/reveal. Reaching the active Browser document bottom auto-hides the composer unless a non-empty draft is focused; explicitly restoring it suppresses another auto-hide until the guest leaves and reaches the bottom again, and device emulation disables this behavior. Empty overlays use a 44px auto-single-line composer joined to a collapsed latest-turn tray; side-chat, Terminal, Files placeholders, blank new-thread, and resuming-thread states stay on their existing non-overlay paths.
- Bottom panel: the v1 bottom panel renders one tab group below the thread/right-panel row and spans the full active session width. It has a top-edge resize handle, defaults to 280px tall, opens when a bottom tab such as Terminal is created or focused, and can be shown or hidden from the fixed global `Toggle bottom panel` button even before any durable bottom tab exists. Empty panel choosers and panel new-tab menus use one capability resolver for Project ownership, attached-thread/cwd state, target panel, and singleton availability. Project-backed sessions retain the standard thread-panel order Review, Terminal, Browser, Files, Side chat. Projectless sessions use Side chat, Browser, Terminal order after eligibility filtering: an attached thread with cwd receives all three, an attached thread without cwd receives Side chat and Browser, and a blank session receives Browser. Right-panel menus append a separated Nodex-only section for DB View and Card Stage when eligible. DB View creates or focuses the active session project's DB tab directly until that project already has one, then opens the project DB destination picker; Card Stage opens the card destination picker with the active session project's cards grouped first.
- Browser tabs: `browser` is a real multi-tab kind. In Electron it renders the Nodex browser surface with Main-owned `<webview>` content scoped by the owning Window Session's `browserViewScopeId`, navigation chrome, local-server new-tab state, device toolbar, zoom/data-clearing menu, retained hidden webview mounting, and browser-specific tab context actions. Two windows viewing the same Session never share or steal guest navigation. A deliberate new-window clone or fork snapshots the source descriptor and remints a target runtime/scope identity. Browser tab context menus put `New tab to the right`, `Reload`, and `Duplicate` before the generic close/move/split actions. Renderer UI dispatches browser commands; it must not imperatively call guest-page navigation methods. In browser runtime it renders a desktop-only unavailable state because Electron webviews are not available.
- The right panel has a left-edge resize handle in regular mode. Full-width mode collapses the thread viewport to zero width, removes the resize handle and inner left border, hides the fixed header center surface, and exposes `Restore panel width` from the right-panel tab header.

## Session And Tab Semantics
- `Database View`: created as ordinary starter Session content for each new Project and pinned by default. Its Core domain record stores the Project's initial View target; each Window Session materializes its own full-width right-panel `db_view` tab only while no local view record exists. The Session can be renamed, unpinned, archived, deleted, opened in a new window, and shown in the normal Session context menu; listing Sessions never recreates deleted domain content, and an intentionally emptied local view remains empty.
- `db_view`: reuses the DB toolbar/view host for kanban, list, toggle-list, canvas, and calendar views. A session can have one DB View tab per target project; selecting an already-open project DB focuses that tab.
- `card_stage`: reuses Card Stage for a project/card config. Single-clicking a card from a Kanban DB view opens or replaces a renderer-local Card Stage preview in the right panel instead of switching to a global Cards stage or creating a durable tab; double-clicking the Kanban card opens a durable Card Stage tab immediately. Command palette card results, thread card links, and explicit Card Stage picker opens remain durable session tabs. A card tab can live in one project session while rendering a card from another project; the tab stays owned by the active session project, while its config project controls the loaded card and history. Terminals requested from that card remain owned by and start in the active Session workspace. Cross-project card tabs show the content project as a compact tab-row prefix before the card title. If the DB tab's group has another right-panel tab group to its right, new card previews or tabs open in the nearest right-side group. If the right panel is full-width and the DB tab is the only right-panel group, opening a DB card first creates a right-side group and opens the preview or durable tab there. Focusing an existing durable Card tab clears any preview in that leaf and preserves the current right-panel width mode. Only the selected tab body mounts; returning mounts a fresh Card Stage view and restores explicitly owned presentation. Card tabs keep their shell stable while board summary or full Card detail hydrates: the toolbar is visible but disabled, the title uses the tab snapshot when available, and only unresolved property/editor regions skeletonize. Once Card Detail is loaded, tab chrome uses its committed Card title projection; while a Card Stage is mounted, authoritative local or remote Y.Text title changes update the tab text, tooltip, and accessible label immediately, with an empty title rendered as `Untitled`. The persisted tab title remains a loading/error fallback and is not rewritten for collaborative title edits. Missing target projects/cards render an explicit empty state only after loading settles instead of showing a blank or misleading tab.
- `terminal`: reuses the Main-owned terminal lifecycle with a Window Session-local descriptor and defaults to the bottom panel. A Project-backed Session starts in its attached Thread cwd or Project root. A projectless Session requires an attached Thread with a non-empty cwd and starts exactly there; it never falls back to the user home or process cwd. Terminal config stores only `terminalSessionId`. Main grants one interactive Window Session lease per PTY; explicit takeover moves the lease, local tab close releases it without killing the process, and explicit kill/backend exit destroys the PTY.
- `browser`: stores optional URL, title, favicon, and device-toolbar restore metadata and renders the Browser sidebar feature. Browser tabs are not view singletons; users can create blank tabs to the right, reload, and duplicate existing Browser tabs from the tab context menu. Session re-home is independent of tabs; descriptors re-resolve under the new domain scope.
- Preview tabs: Files and Browser can open as renderer-local previews in either right or bottom panel. Kanban DB-view card clicks open `card_stage` as a right-panel renderer-local preview in the nearest right-side group, creating a right-side group first when the right panel is full-width with only the DB group. Each panel leaf has at most one italic preview; opening another preview in that leaf replaces it. Preview tabs are omitted from the persisted Window Session view until the user interacts with the preview body, chooses `Pin tab`, or double-clicks the preview tab label, at which point the local descriptor is persisted and activated. Card Stage previews keep a persisted-compatible client tab id so pinning preserves identity even though the selected body follows the normal fresh-view lifecycle. Card Stage close/delete controls are preview-safe and close/delete without first pinning the preview.
- Side chat tabs: Side chat is a renderer-local action/tab family, not a persisted `WorkbenchSessionViewTab` kind. Side chat actions create renderer-local loading tabs (`sidechat-loading:<parentThreadId>:<index>`) in the requested panel, then replace them with closable ready tabs (`sidechat:<threadId>`) after the main process starts an ephemeral fork. Side chat titles are `Side chat`, then `Side chat 2`, `Side chat 3`, and so on for the Session view. They can move between the right and bottom panels in renderer memory, but they are never persisted, pinned, archived, listed as normal Project Threads, or restored after app restart.
- Ready side-chat tabs render the local conversation body and composer without the normal thread-stage title header; the side-chat tab itself is the only top title row.
- Side-chat start input contains only parent conversation identity and optional prompt/settings. Main derives execution context from the parent detail. Project-backed parent navigation remains `project:<id>/session:<id>/thread:<id>`; projectless navigation is `session:<id>/thread:<id>` and never fabricates `project:null`.
- Session-thread links are the durable local ownership path for Codex threads. Cards may open as session tabs or mention threads, but they do not own Codex threads.

## Storage Ownership
- SQLite owns shared Project Session domain data:
  - `project_sessions`: nullable Project id, `no_thread_fallback_title`, order, pin/archive/unread state, and the semantic `database_starter` marker.
  - `project_session_threads`: optional Session-to-Thread attachments; canonical Thread metadata lives in `codex_threads`.
  - Session lists return a derived `displayTitle`; attached Sessions prefer `codex_threads.thread_name`/preview and only fall back to `no_thread_fallback_title`.
- Main's revisioned Window Session catalog owns active Project, active Session, settings route visibility, right/bottom panel trees, sizes, selection/MRU, all persisted tab descriptors, Browser view scope, and cold-restore layout. Each Session id maps to one strict `WorkbenchSessionViewSnapshot`. Writes use ownership validation, compare-and-swap `layoutRevision`, bounded codecs, atomic replacement, and fsync.
- App-window Back/Forward history and previews remain renderer-local because they are live interaction state, not cold-restore authority.
- Renderer server-state cache owns the hot domain-only Project Session read path: sidebar rows come from Project/projectless summaries, recently selected or hovered Sessions hydrate one full detail by Session id, and mutations that return a full Session seed that detail cache. Full Project Session list reads are reserved for slow domain paths and never carry tabs/layout.
- Renderer task presentation mounts exactly one selected session page and one selected body per panel leaf. Switching disposes the previous React view; scoped renderer state restores explicit presentation, while Query and the Codex/Browser/Terminal/Document Modules preserve their own data and runtime continuity.
- Renderer-local side chat state owns temporary tab identity, loading/ready/expired status, and panel placement. The backing app-server thread stays in the main-process conversation cache only while live and is discarded when the tab closes.
- Core schema v90 removes historical `project_session_tabs`, `panel_state_json`, and `left_pane_collapsed`. It preserves Session/Thread/Project/content data and extracts at most one valid Database View target into `initial_database_view_id`; the old shared arrangement is intentionally discarded because no Window Session owner can be inferred. Core schema v93 replaces that retained pointer with the `database_starter` marker; the presented View always resolves from Database authority at materialization time.
- Old stage-rail/window layout snapshots are best-effort inputs for active project/session defaults only; they are not authoritative shared session data.

## Navigation
- Session switching synchronously unmounts the previous task page and mounts the selected thread page plus its right and bottom panel groups. Exactly one task page and one route header exist.
- Session switching reuses cached summary/detail and authoritative Module state, including cross-project sessions, without calling the full project-session list or forcing a board fetch solely because the session id changed. Returning to a task or panel tab creates a fresh React view and restores only explicitly owned presentation such as Composer drafts, transcript state, and registered scroll snapshots; ephemeral component-local state resets.
- App-window Back/Forward controls are available as titlebar buttons, command palette commands, `Cmd/Ctrl+[` and `Cmd/Ctrl+]`, desktop mouse Back/Forward buttons, and the macOS application menu; all routes enter the same shell-owned navigation executor. The command ids are `navigateBack` and `navigateForward`, labels are `Back` and `Forward`, and the disabled state follows the shell-local back/forward stacks.
- Each history snapshot stores the visible workbench context: active project id, active session id, active DB view, right/bottom active tab ids, right/bottom collapsed state, and right-panel full-width state. Settings routes, command palette state, task search, and browser-sidebar webview history stay outside this stack.
- Tab switching persists only through the owning Window Session view's panel leaf layout.
- Browser-sidebar webview navigation remains separate from app-window history. Browser tab `canGoBack` / `canGoForward` and `webContents.goBack` / `goForward` must not drive the top-left workbench Back/Forward buttons.
- Review is a session singleton tab kind across both right and bottom panels. DB View is deduped by target project, so creation affordances keep showing DB View after the current project DB exists and use the picker for other project DBs. Browser is deliberately multi-tab; creation affordances keep showing Browser even when Browser tabs already exist, and Browser tab context menus add `New tab to the right`, `Reload`, and `Duplicate` before the generic close actions.
- Tab context menus append generic close actions after feature-provided items: `Close`, `Close other tabs`, and `Close tabs to the right`. `Close other tabs` is enabled only when another closable tab exists in the same leaf; `Close tabs to the right` is enabled only when at least one closable tab follows the current tab. Cross-panel move and split actions remain below the generic close block when available.
- Tab reorder mutates only the Window Session view's panel tree; no Core Session mutation or cross-window invalidation occurs.
- Closing a persisted local tab removes that descriptor from the Window Session view. Every tab is closable independently of how many sibling tabs exist; if it was the panel's final persisted tab, the local reducer collapses the panel and retains the final empty group as its fallback. Terminal backend exit, including a user typing `exit`, removes matching local descriptors after Main publishes exit. Closing a Terminal tab normally releases its Window Session lease without killing the PTY. Closing a preview drops only renderer-local preview state and collapses that panel if it has no persisted tabs. A `Database View` tab follows the same local close rules as any other persisted tab.
- Closing a side-chat tab removes the tab immediately and sends a best-effort discard request in the background. If the backing temporary thread is missing, the tab renders an expired panel with `Start new side chat`, which recreates from the saved parent thread id and replaces the expired tab with the new temporary thread.
- Task routing and selected-session changes are synchronous so route cleanup/setup and header ownership complete in one deterministic lifecycle. Lower-priority data refreshes may still use transitions, but routing itself must not have warm/cold branches.
- React keys should reset only the active session/tab body that changed; switching projects or sessions must not force unrelated global stores to remount.
- When a full-width right-panel tab collapses the thread viewport to zero width, the selected route, Composer, footer, and lifecycle coordinator stay active while transcript children unmount. Restoring regular width remounts the transcript from its explicit snapshot.
- Only the selected task may register shell side effects such as global header actions, summary panels, composer overlay targets, panel measurement refs, or visible Browser webview ids.

## Keyboard Model
- Existing global command palette, settings, and editor shortcuts remain in force. Undo/redo is local to the focused editable surface; the shell owns no Project-wide history stack.
- The previous stage-order shortcuts (`View -> Card -> Thread -> Diff`) are retired as primary shell semantics.
- Project/session/tab keyboard shortcuts should be introduced against the new hierarchy: project folder, session row, thread page, and right/bottom panel tab groups.
- `Cmd/Ctrl+J` executes the shell-global `toggleBottomPanel` command and shows or hides the active session bottom panel. Toolbar, command palette, browser-runtime keyboard handling, and the desktop application menu share the same shell executor; Electron owns the desktop accelerator so one keypress cannot toggle twice. It works from editable and desktop Browser surfaces, preserves explicit user unassignment, and safely no-ops when no session is active.
- `Ctrl+\`` focuses an existing session terminal tab or creates one in the bottom panel. `Alt+Cmd/Ctrl+S` starts Side chat in the right panel. The global terminal drawer is not part of the project-session shell model.
- `Cmd/Ctrl+Shift+[` and `Cmd/Ctrl+Shift+]` cycle the previous/next tab for the focused right or bottom panel tab group. Cycling resolves the nearest split leaf or the last focused leaf from the native menu route, wraps within that leaf, works from NFM editor content in that leaf, no-ops for zero or one tab, and does not replace plain `Cmd/Ctrl+[` / `Cmd/Ctrl+]` app-window Back/Forward.
- `Cmd/Ctrl+W` closes the active closable tab in the focused right or bottom panel tab group by using the same `closePanelTab` path as tab chrome. It works from NFM editor content in that leaf, ignores input fields and dialogs, no-ops for non-closable tabs, and must not close the app window. After close, keyboard/menu routing stays within the same split leaf and reveals the most recently active remaining tab, with right-neighbor then left-neighbor fallback only when MRU cannot answer. Close-button and middle-click single-tab closes use the same MRU routing. On macOS, Close Window uses `Cmd+Shift+W`.

## UI Contract
- Surfaces should use the generated theme layers and token classes before adding local CSS.
- Left titlebar navigation uses one grouped toolbar rail. Back renders lucide `ArrowLeft` with `icon-xs`; Forward reuses the same icon with `icon-xs -scale-x-100`. Each button has matching `aria-label`, `title`, tooltip text, command palette title, and disabled styling. On macOS the collapsed sidebar titlebar reserves `208px` total and renders the compact `New chat` edit/new-chat glyph after Forward.
- Tabs are dense, use hover-revealed close actions, support pointer reorder through the shared tab strip, and scroll horizontally when the user wheels over an overflowing tab row. Tabs share equal responsive widths regardless of title length, growing together from 90px up to 160px before the row overflows. Direct close-button clicks and middle-click closes enter a rapid-close mode that temporarily locks the whole row to the target tab's current width until the pointer leaves the tab row, so repeated closes stay under one pointer position. Rapid close affects only tab-row measurement and pointer stability; the revealed tab after any single-tab close is still chosen by same-leaf most-recently-active routing. Each tab item exposes a hover tooltip with its full title; cross-project Card Stage tooltips include both the card title and the content project.
- Empty-panel action choosers use the Codex row-stack layout: `p-2` host, centered `max-w-xl` stack, `gap-1 px-panel`, full-width `min-h-10` rounded rows with secondary background, `icon-xs` leading icons, `text-sm font-normal` labels, and right-aligned compact shortcut labels. The primary option order is Review (`Ctrl+Shift+G`), Terminal (`Ctrl+\``), Browser (`Cmd/Ctrl+T`), Files (`Cmd/Ctrl+Shift+E`), and Side chat (`Alt+Cmd/Ctrl+S`). Right-panel choosers append a divider plus Nodex-only DB View and Card Stage rows so project-native database and card workflows remain directly reachable without changing the Codex order. Those Nodex rows open a 330px move-to-style picker with a 28px search input, grouped `DB` / `Card` result semantics, command-palette-aligned fuzzy/prefix matching, delayed loading, empty, and error states. Card-only picker results split matching cards into `Current project` first and `Other projects` second, omitting empty groups.
- Side chat entry points are available from the empty-panel action chooser, panel new-tab menu, attached-thread header overflow menu (`Open side chat`), composer slash command (`/side`), and the thread selected-text `Ask in side chat` overlay. Explicit prompt entry points such as `/side <prompt>` submit the prompt into the temporary side chat; selected-text overlay entry points create the side chat and prefill the side composer without submitting. Creating a side chat from within a side chat is blocked with `'/side' is unavailable in side chats. Return to the main thread first`.
- Keep `Timeline` hidden until Nodex has a first-class tab kind and eligibility model for it.
- Project/session rows should be information-dense and shallow: folder disclosure, project label, derived session `displayTitle`, and subtle thread-attached indicator.
- Project folders are sortable with pointer and keyboard input. Pointer drag starts after 6px of movement from the project-label activator; `onDragMove` and `onDragOver` both refresh intent so crossing the same target row's midpoint resolves a precise before/after boundary, while keyboard sorting uses the translated active-row midpoint. During drag, the source stays in its original slot as an inert 20% ghost, sibling folders do not live-shift, and a compact body-level folder preview follows the pointer. The final insertion boundary is shown without changing list layout by a 2px link-blue rail with an outlined leading dot. Normal and pinned lists persist through their separate project-order APIs, unchanged boundaries do not write, and failed writes clear only their matching optimistic projection before surfacing the shared reorder error. An empty Pinned target reveals its indicator only while actually hovered.
- The thread page content frame keeps the shell top border but forces the frame top offset to `0px`, so the thread title row starts at the top instead of below an empty toolbar band. The global top-right controls are reserved inside that title row through the thread header right-reserve area.
- Do not reintroduce the stage rail as a compatibility layer. DB view, Card Stage, Thread, Diff/review, and Terminal implementations should remain reusable bodies behind sessions and tabs.

## Storybook And Testing
- Storybook coverage lives in `src/renderer/components/workbench/workbench-session-shell.stories.tsx` for mixed tabs, cross-project card tabs, empty right/bottom action grids, attached thread page, collapsed right panel, full-width right panel, long names, and enabled/disabled left titlebar navigation chrome. Focused sidebar project-sort, insertion-indicator, pinned-project, and empty Pinned drop-target states live in `src/renderer/components/workbench/left-sidebar.stories.tsx`. Focused preview tab states, including the Card Stage preview tab, live in `src/renderer/components/workbench/app-shell-tabs.stories.tsx`; focused side-chat panel state stories live in `src/renderer/components/workbench/workbench-side-chat.stories.tsx`.
- Focused right-panel composer overlay stories live in `src/renderer/features/local-conversation/view/right-panel-composer-overlay.stories.tsx` and cover full-width Review, compact Browser, bottom-panel offset, running-thread Stop, and reduced-motion states.
- Unit tests should cover schema migration from legacy Overview rows, `Database View` starter session creation, tab config validation, session ordering, tab ordering, session-thread startup, and the absence of attach/detach toolbar controls.
- Renderer tests should cover project expansion, session loading/switching, `Database View` ordinary row behavior, right-panel collapse/full-width behavior, bottom-panel terminal behavior, tab selection, tab reorder, cross-panel move, and each tab kind.
